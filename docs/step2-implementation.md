# 2단계 구현 기록

2026-09-28. `scenario-branching.md`의 1단계 설계를 실행 코드에 연결했다.

## 적용 내용

- `backend/data/branches.py`: 3개 시나리오의 안전/위험 대사, 질문, 결말 정의. 기존 시나리오 ID와 단계별 점수 규칙은 유지한다.
- `backend/services/llm_service.py`: 사용자 답변을 근거 원문·예정/완료/부정·과거 여부가 있는 행동으로 추출한다. JSON 스키마와 근거 원문을 검증한다. 실패하면 규칙 분석으로 전환한다.
- `backend/services/branch_analysis.py`: 명확한 표현만 처리하는 보수적 규칙 분석과 서버의 안전/위험 판정을 담당한다. LLM과 명확한 규칙 결과가 다르면 재질문한다.
- `backend/services/multi_stage_service.py`: 실제 대화 이력과 완료 행동을 보존하며 분기를 이동한다. 재질문은 같은 단계에서 2회까지 가능하다. 통화 종료·거래 철회 시 조기 종료하고, 과거 완료된 위험 행동이 있으면 노출 후 중단으로 구분한다.
- `backend/routers/multi_stage.py`: 답변 길이를 2~500자로 제한하고 요청 ID와 예상 단계를 받는다.
- `frontend/src/App.tsx`: 단계별 질문, 분석 실패 안내, 재질문, 종료 결과를 연결한다. 재시도 시 같은 요청 ID를 사용해 단계 중복 진행을 막는다.

## 대사 생성 방식

LLM이 이야기의 사실을 자유롭게 추가하지 않도록, 서버가 고른 분기의 기본 대사와 같은 의미의 도입 문구를 더한 후보 중에서 선택하게 했다. `safe`에서는 회피·물러남, `risky`에서는 안심·요구 지속이라는 태도가 유지된다. 선택 형식이 잘못되거나 호출이 실패하면 기본 대사를 사용한다.

따라서 이번 구현은 자유로운 장문 대화 생성이 아니다. 분기와 사실의 일관성을 우선하는 제한된 대사 선택 방식이다. 향후 대사 다양성을 늘릴 때에는 해당 분기에서 허용되는 후보를 추가할 수 있다.

## 결과와 점수

- 최종 위험도는 누적 점수 임계값 대신 결말에 연결한다. 조기 종료한 사용자를 응답 수 때문에 불리하게 평가하지 않는다.
- 기존 시나리오 규칙의 점수는 원점수로 남기되 행동 분석과 맞는 규칙만 반영한다. 정규화 공식은 추가하지 않았다.
- 화면에는 비교하기 어려운 원점수 대신 응답 완료 단계 수와 결말 설명을 표시한다.
- 판단 자료 부족은 `risk_level: unknown`, `score: null`이다. 이전에 확인된 행동 목록은 남는다.

## API 변경

`POST /api/multi-stage/respond` 요청에 선택 필드 `request_id`, `expected_stage`가 추가됐다. 프론트엔드는 두 값을 모두 전송한다. 같은 요청 ID와 답변의 재전송은 이전 응답을 반환한다. ID를 재사용하면서 답변을 바꾸거나 오래된 단계를 제출하면 오류다.

진행 응답에는 `question`, `branch`, `status`, `completed_stage_count`, `ending_type`이 추가됐다. `status`는 `advanced`, `clarification`, `analysis_unavailable`, `finished` 중 하나다. 기존 `stage_score` 대신 결과의 `stage_results`에서 단계별 점수를 확인한다.

분석 실패 후 규칙으로도 판단하지 못하면 `analysis_unavailable`을 반환한다. 세션의 대화·단계·점수·재질문 횟수는 바꾸지 않으므로 동일 답변을 재시도할 수 있다. 진행 중에는 최종 결과 API를 조회할 수 없다.

테스트용 `/next-response-test`에는 `branch`가 필수다.

## 검증과 남은 범위

백엔드 테스트 실행: `backend`에서 `.venv/Scripts/python.exe -m unittest test_branching -v`.

프론트엔드 검증: `frontend`에서 `npm run build`, `npm run lint`.

자동 테스트는 Gemini 응답을 대체하여 분기·재질문·종료·실패·JSON 검증·실제 API 흐름을 확인한다. 실제 Gemini 서비스의 응답 품질과 지연시간, 브라우저 수동 시연은 별도 확인 대상이다. 자유 서술형 전체를 정규식으로 이해하는 것은 아니므로, LLM이 없으면 명확한 표현만 처리하고 나머지는 재시도를 안내한다.

로그인, DB 보관함, 퀴즈 추가, 전체 UI 개편, 배포는 이번 작업에 포함하지 않았다. 세션은 여전히 서버 메모리에 저장된다.

검증 결과: 백엔드 자동 테스트 22개 통과, 프론트엔드 프로덕션 빌드 및 ESLint 통과. 실제 Gemini API는 호출하지 않았다.
